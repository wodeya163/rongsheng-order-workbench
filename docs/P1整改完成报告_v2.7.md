## 二、P1-5 手工合计保护

**问题**：导入时文件里写了「价税合计 1000」，但明细只有 800.30；之后只要增删一行明细，`_sync_totals(order_id)` 就用 Σ明细 把 1000 覆盖成 800.30，对账时金额凭空变了。

**做法**：

1. `orders` 增两列 `amount_manual` / `item_qty_manual`（0=派生，1=人工声明）。
2. 建单 / 导入时显式给了值 → 置 1；`create_order` 与 `_sync_totals` 双处一致。
3. `_sync_totals()` 只重算「未上锁」的字段；显式传值仍可改并重新上锁。
4. 新增 `OrderService.reset_totals()`：清锁 + 立即重算 + 写审计。
5. 界面：订单结果表末列「汇总口径」显示 `自动` / `金额手工` / `项数手工`；右键与左侧操作列表均有「恢复自动汇总（选中订单）」。

**迁移 v3 的回填规则**（关键）：对每张历史订单比较「表头金额 vs Σ明细」——相等视为派生（0），不等则标记为手工（1），避免升级后第一次改明细就把历史口径改掉。真实库 306 单实测：**0 单被误标**（源表金额本就等于明细汇总）。

## 三、P1-6 金额精度

| 项 | 之前 | 现在 |
|---|---|---|
| 明细总价 | `round(qty*price, 2)`（float 四舍五入） | `money.mul()` → Decimal `ROUND_HALF_UP` |
| Σ明细 | `round(sum(float...), 2)` | `money.sum2()` Decimal 累加 |
| 落库 | 原始 float | `money.to_db()` / `to_db_price()` 先量化（分 / 4 位） |
| 读回 | float 直接加减 | `Decimal(str(x))`，不带二进制尾数 |

实测：10 行「1 × 0.1」合计 `1.0`（旧写法 0.9999999999999999）；`1.005 → 1.01`、`2.675 → 2.68`。
**为什么不是整数分存储**：金额列语义不变、存量无需重建、读写路径零改动；代价是 >2^53 分不可表示（业务不可能）。已在 `money.py` 顶部写明升级路径。

顺带修掉一个隐藏矛盾：维护界面改明细单价时，总价以前不会跟着变（单价 100→200，总价还是 100）。现在未显式改总价时按「数量×单价」重算。

## 四、P1-7 异步解析

```
选择文件 → 按钮禁用 + 「正在识别：xxx.pdf …（PDF/扫描件需要几秒）」
        → QThreadPool 跑 docread.read_source()
        → 完成信号回主线程 → 填 17 列预览 / 失败提示并恢复按钮
```

- 回调全部在主线程（Qt 信号自动排队），可安全改界面；
- 任务挂在对话框 `_jobs` 上防 GC，完成后自动摘除；
- 测试/脚本用 `_load_blocking()`，与异步版走同一段填充逻辑；
- `async_task.wait_all()` 供离屏测试等待。

## 五、P1-8 打包瘦身

| 指标 | v2.6 | v2.7 | 变化 |
|---|---|---|---|
| `dist/ProductSuite_v2.2` 总体积 | 505 MB（476 MB `_internal` + 28.9 MB exe） | **178 MB** | **-64.7%** |
| 其中 PySide6 | 92 MB | 92 MB | Qt 应用的地板 |
| 已清除 | pandas / numpy / pyarrow / numba / llvmlite（~200 MB）、PyMuPDF（37.5 MB）、pygame（7 MB）、Pythonwin（6.4 MB） | — | — |

**根因**：`--collect-submodules v2` 会把 `v2/tests` 收进包，测试里 `import fitz` 连带拉入 PyMuPDF 全家桶；pandas 又拉 numpy/pyarrow/numba/llvmlite。

**现在**：`--collect-submodules v2.core` + 19 条 `--exclude-module`（含构建机上无关的 pygame / pywin32 IDE 组件）。

**打包后实测（不是估的）**：

```

  DDL 自检: 15 张表可创建
  文档识别: docx=OK　PDF=OK　OCR=OK chi_sim+eng
  → exit 0

ProductSuite_v2.2.exe --parse-check  build/_parsecheck/sample.xlsx   表格   2 行 / 命中 6
ProductSuite_v2.2.exe --parse-check  build/_parsecheck/sample.docx   Word    2 行 / 命中 6
ProductSuite_v2.2.exe --parse-check  build/_parsecheck/sample.pdf    PDF     2 行 / 命中 5
ProductSuite_v2.2.exe --parse-check  build/_parsecheck/sample.png    图片    2 行 / 命中 5
  → 四个通道在瘦身包里全部可用
```

新增 `--parse-check <文件>`：出问题时让用户直接跑一遍，就能判断是「文件本身读不出来」还是「程序缺依赖」。
