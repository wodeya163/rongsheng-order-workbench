### 1.2 三个致命的结构性缺口（决定不能"加两张表"了事）

1. **没有单据头**：`project` 只是产品行里的一个自由文本，不存在「一张询价单 / 一张询配码单」实体，无法承载客户、日期、状态、负责人、整单金额。
2. **没有明细行 ID**：现有 `products.id` 是产品库主键，不是「单据第 N 项」。用户要求"关联到**哪一个询配码的哪一项**"，必须有一个稳定、可被引用的 `code_item_id`。
3. **没有任何外键**：跨模块关联只能靠字符串匹配，改一个规格就断链，无法做数量守恒与追溯。

> **设计决策（P0）**：v2 采用**全新 `v2/` 包 + 新库 `erp.db`**，现有 `app/` 与 `products.db` 保持只读、原样保留；通过一次性迁移脚本把历史数据导入新库，v1.5 功能作为「询报价」域的一个视图复用。
> 理由：直接在 `products` 上做 ALTER 加外键会把旧代码、Excel 导入导出、打包链路全部牵连，风险远大于另起一层。

## 2. 术语与假设（**需张哥拍板，见 §11**）

| 术语 | 本框架采用的定义 | 依据 |
|---|---|---|
| 询报价管理 | 客户询价 → 录入明细 → 计算对外报价 → 报价 → 中标判定。即现有 v1.5 功能的单据化升级 | 现有 `app/calc.py` |
| **询配码** | 中标（或拟中标）后形成的**配置/物料配码单**：一张单（有唯一"询配码"编号）+ 若干明细项，每项含品名、规格、材质、执行标准、图号、数量、技术要求，用于向生产下发 | 管件行业 RFQ 惯例：询价单据号 + 物料行号 + `90°弯头\DN250\S=5\20\GB/T12459` 式规格串 |
| 询配码的"一项" | `code_items` 表的一行，拥有全局唯一 ID 与单内行号，是**被排产引用的最小粒度** | 用户原话"哪一个询配码的哪一项" |
| 生产排产管理 | 以「生产项目」为容器，下挂工序任务；项目可关联一个或多个询配码明细项 | — |
| "管理管件" | 按「面向管件产品的管理软件」理解；若实际指"管理软件"，不影响架构 | 用户原文 |

**两条口径假设（默认已按此实现，可改）**
- A1：询配码**通常由中标的询价单转换生成**，也允许手工独立建单（`source_quote_id` 可空）。
- A2：一个排产项目**可挂多个询配码项**，一个询配码项也**可拆到多个批次/项目排产** → 采用多对多关联表，而不是在项目表上加一个 `code_item_id` 字段。这样一对一、一对多、多对多三种口径都不用改表。

## 5. 核心打通设计（本次升级的重点）

### 5.1 关联表 `production_links`

用户要求"在生产排产管理项目中可以关联该项目来自于哪一个询配码的哪一项"。落地为：

```sql
CREATE TABLE production_links (
    id                      INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id              INTEGER NOT NULL REFERENCES production_projects(id) ON DELETE CASCADE,
    code_item_id            INTEGER NOT NULL REFERENCES code_items(id) ON DELETE RESTRICT,
    allocated_qty           REAL NOT NULL CHECK (allocated_qty > 0),
    -- ↓ 快照：建链瞬间的上游原貌，上游后续改名/改规格不影响历史
    code_no_snapshot        TEXT NOT NULL,   -- 询配码单号，如 XPM-202611-0001
    item_code_snapshot      TEXT NOT NULL,   -- 项号，如 XPM-202611-0001-02
    item_name_snapshot      TEXT,
    spec_snapshot           TEXT,
    source_quote_no_snapshot TEXT,           -- 一路穿透到原始询价单号
    created_by              TEXT,
    created_at              TEXT,
    UNIQUE (project_id, code_item_id)
);
```

**为什么要用独立关联表，而不是在 `production_projects` 上加 `code_item_id`：**

| 场景 | 单外键方案 | 关联表方案 |
|---|---|---|
| 一个项目只做一项 | ✅ | ✅ |
| 一个项目含多个询配码项 | ❌ 需改表 | ✅ |
| 一项拆两批排产（分批交货） | ❌ 数量无法分摊 | ✅ `allocated_qty` 分账 |
| 追溯"这项一共排了多少、还剩多少" | 全表扫描 | 一次 `SUM` 聚合 |
| 关联时记录当时规格/图号 | ❌ | ✅ 快照字段 |

### 5.2 数量守恒（硬规则）

```
可排量(code_item) = code_items.qty − SUM(production_links.allocated_qty WHERE code_item_id = ?)
建链校验：allocated_qty ≤ 可排量，否则抛 OverAllocationError
```

- 建链、改量、删链全部在同一事务内完成；删链后重算 `code_items.status` 与 `code_orders.status`。
- 状态回写：`待配码 → 已配码 → 部分排产(0<已排<总量) → 已排满(已排=总量)`。

### 5.3 双向穿透查询（两个方向的 API）

| 方向 | API | 返回 |
|---|---|---|
| 从生产反查来源 | `TraceService.from_production(project_id)` | 每个关联项 → 询配码单号/项号/规格/数量 → 原始询价单号 → 原报价明细 → 客户、项目名 |
| 从询配码正查去向 | `TraceService.from_code_item(item_id)` | 该项被哪些生产项目领用、各领多少、项目状态、计划/实际完工日期 |

界面上就是第 ④ 个 Tab：**点一个生产项目，一眼看到它由哪几张询配码单的哪几项构成，一直能追到最初那张询价单**。

### 5.4 三类追溯字段的分工

| 类型 | 例子 | 用途 |
|---|---|---|
| 结构化外键 | `code_item_id`, `source_quote_id`, `source_quote_item_id` | 实时联查、状态回写、数量守恒 |
| 快照文本 | `code_no_snapshot`, `spec_snapshot` | 历史原貌、单据打印、上游变更免疫 |
| 审计日志 | `audit_log` | 谁在什么时候改了关联/数量 |

## 6. 数据库设计（DDL 摘要，全量见 `v2/core/schema.sql`）

| 表 | 主键 | 主要索引 | 约束要点 |
|---|---|---|---|
| `quote_orders` | id | `uk_doc_no` | `doc_no` 唯一；`status` 枚举校验 |
| `quote_items` | id | `idx_qi_quote`, `idx_qi_legacy` | `(quote_id, line_no)` 唯一；`quote_ratio>0` |
| `code_orders` | id | `uk_doc_no`, `idx_co_source` | `source_quote_id` 可空（支持手工建单） |
| `code_items` | id | `uk_co_itemcode`, `idx_ci_source_quote_item` | `(code_order_id, item_code)` 唯一；`qty>0` |
| `production_projects` | id | `uk_doc_no`, `idx_pp_status` | 计划起止日期一致性由服务层校验 |
| `production_tasks` | id | `idx_pt_project` | `finished_qty ≤ qty` |
| `production_links` | id | `idx_pl_item`, `idx_pl_project` | `(project_id, code_item_id)` 唯一；`ON DELETE RESTRICT` 防误删已排产的配码项 |
| `doc_sequence` | (prefix, period) | 主键 | 取号在同一个事务里 `UPDATE ... RETURNING` |
| `audit_log` | id | `idx_al_entity` | 只增不改 |

**金额口径沿用 v1.5，不改算法**：`对外报价 = 采购价 ÷ 报价比率`（`app/calc.py:30-34`），v2 中作为 `quote_items` 的**计算列**由服务层统一产出，避免旧版"文档写了列、库里没有"的不一致。

## 7. 状态机与编码规则

### 7.1 状态迁移（服务层集中校验，禁止界面直接写库）

| 实体 | 状态流 |
|---|---|
| 询价单 | `草稿 → 已报价 → 中标 / 未中标 / 作废` |
| 询配码单 | `草稿 → 已确认 → 已下发 → 部分排产 → 排产完成 → 关闭` |
| 询配码项 | `待配码 → 已配码 → 部分排产 → 已排满` |
| 生产项目 | `待排 → 已排产 → 生产中 → 完工 → 已交付` |

> 只有 `已报价 + 中标` 的询价单允许一键转询配码；`已确认` 以上的询配码项才允许被排产引用（可由配置项放宽）。

### 7.2 单号规则

| 对象 | 格式 | 示例 |
|---|---|---|
| 询价单 | `XJ-YYYYMM-NNNN` | `XJ-202611-0001` |
| 询配码单 | `XPM-YYYYMM-NNNN` | `XPM-202611-0001` |
| 询配码明细项 | `<询配码单号>-<两位行号>` | `XPM-202611-0001-02` |
| 生产项目 | `SC-YYYYMM-NNNN` | `SC-202611-0001` |
| 工序任务 | `<生产项目号>-T<两位序号>` | `SC-202611-0001-T01` |

由 `doc_sequence(prefix, period, next_val)` 在事务内取号，避免同月并发重号。

## 12. 待确认口径清单（**下一轮请张哥拍板，我已给默认值**）

| # | 问题 | 我的默认假设 | 影响面 |
|---|---|---|---|
| Q1 | "询配码"是「一张单据 + 多个物料项」，还是「单个物料的一个编码」？ | **单据 + 明细项两层**（因为要"哪一项"） | 若理解错，`code_orders` 层需去掉，改动中等 |
| Q2 | 询配码是否必须来自中标询价单？ | 通常转换生成，**允许手工独立建单** | `source_quote_id` 可空 |
| Q3 | 一个生产项目能挂几个询配码项？一项能否分批排产？ | **多对多 + 数量分摊** | 若严格一对一，可简化为项目表单外键 |
| Q4 | 排产数量能否超过询配码项数量（余量/备品）？ | **禁止，硬校验**；确需放宽改为可配置容差 | 数量守恒规则 |
| Q5 | "哪一项"指的是行号（第 2 项）还是配码号（如 `XPM-...-02`）？ | 两者都存：`line_no` + `item_code` | 界面显示口径 |
| Q6 | 部署形态：继续单机桌面，还是要多人共享？ | **先单机 SQLite**，但 Repository 已隔离，后续可平滑换库 | 决定是否提前上权限/并发控制 |
