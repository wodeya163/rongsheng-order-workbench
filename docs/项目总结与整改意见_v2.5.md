### 1.2 技术架构

```
v2/
├── core/        13 个模块 · 3,300 行   基础设施：db / schema / codegen / fields / excelio
│                                       docread（744 行，多格式解析）/ worddoc / errors / integrity
├── domains/      7 个模块 · 2,600 行   业务服务：bid / partcode / order / production / schedule
│                                       maintenance（维护与级联校验）/ trace（溯源）
├── ui/           4 个模块 · 4,151 行   界面：main_window_v2（1,911）/ dialogs（1,354）/ theme（555）/ query_panel（331）
├── migration/                           v1.5 → v2 数据迁移
└── tests/        7 个文件 · 2,894 行   140 项 + 24 subtests，全绿（14.16s）
```

分层纪律良好：`core` 不依赖 `domains`，`domains` 不依赖 `ui`，业务异常统一继承 `BusinessError`，界面用 `_run()` 统一兜底。这一点在 Python 桌面项目里属于上乘。

### 1.3 数据模型（14 张表）

| 域 | 表 | 核心约束 |
|---|---|---|
| 支撑 | `doc_sequence` / `audit_log` | 事务内取号，防同月重号 |
| 询报价 | `bid_projects` / `bid_items` | 中标 → 内部订单（`uq_internal_order_per_bid` 唯一索引保证一标一单） |
| 询配码 | `code_projects` / `code_items` | 与域 1 零外键；`qty_reference` 虚值不参与守恒 |
| 订单枢纽 | `orders` / `order_items` | `qty_ordered` 唯一实值锚点；`CHECK` 保证内外单来源互斥 |
| 生产 | `production_projects` / `production_tasks` / `production_links` | `Σ allocated_qty ≤ qty_ordered`，`UNIQUE(project_id, order_item_id)` |
| 排产单 | `order_schedules` / `order_schedule_files` | 一明细一单 `order_item_id UNIQUE`，`status_before` 支持状态回退 |

设计上最有价值的三点：① 数量守恒只有一条锚（订单明细实值），杜绝了"询配码虚值污染排产"这类系统性错误；② 快照字段（`order_no_snapshot` 等）让溯源不依赖上游是否被改；③ `CHECK` 与唯一索引把业务红线下沉到数据库，不只靠代码自觉。

### 1.4 规模与质量实测

| 指标 | 实测值 | 评价 |
|---|---|---|
| Python 代码 | 38 文件 / 13,336 行（测试 2,894 行，占 21.7%） | 中等规模，单机应用合理 |
| 最大单文件 | `main_window_v2.py` 1,911 行 / 90+ 方法 | **偏大，已是上帝类** |
| 自动化测试 | v2 140 项 + 24 subtests 全绿；v1.5 36 项 | 覆盖服务层扎实 |
| 打包产物 | exe 28.9 MB + `_internal` **476 MB** | **严重超标**（见 P1-8） |
| 启动耗时 | exe `--check` 1.41s；源码 Qt 导入 0.18s + 主窗口模块 0.94s + 建窗 0.20s | 可接受 |
| 数据库现状 | 14 张表，**全部 0 行** | **真实业务尚未入库** |
| 日志 | 全项目 0 处 `logging` / `excepthook` | **缺失** |

> 结论：**功能完成度高、业务建模扎实，但"可交付给业务使用"还差最后一公里**——真实数据未迁、无日志、无备份、附件不可迁移。

## 二、缺陷清单与整改意见

优先级：P0 = 影响业务上线/数据安全，必须在正式使用前解决；P1 = 影响体验或数据准确性，1–2 个迭代内解决；P2 = 工程质量，随迭代偿还。

> **2026-11-07 更新**：P0-1 ~ P0-4 已全部完成，实施细节与验收证据见 `docs/P0整改完成报告_v2.6.md`。
> 本章保留原始缺陷分析，作为整改追溯依据。

### P0-1 真实业务数据尚未迁移（阻塞上线）✅ 已完成

**现象**：`dist/ProductSuite_v2.2/data/erp.db` 中 `bid_projects / code_projects / orders / order_items / production_projects / order_schedules` 计数全部为 0；真实数据仍在 `销售订单汇总（24年7月-26年）.xlsx`（306 单 / 734 行）。

**影响**：程序目前只是"能跑的空壳"，所有 Q8–Q14 口径都还没被真实数据检验。

**整改**：
1. 迁移前整目录备份 `data/`（含 `products.db`、`attachments/`）；
2. 跑 `python -m v2.migration.migrate_v15`，产出"迁移报告"（成功/跳过/冲突三类计数）；
3. 抽 5 张订单（覆盖内部单、外部单、多批次单）做人工对账：明细行数、`Σ qty_ordered`、`Σ amount`、订单头 8 字段；
4. 跑 `v2.domains.trace` 的一致性检查，确认 `Σ allocated_qty ≤ qty_ordered` 无超排；
5. 对账通过后才切换正式库，旧库只读保留 30 天。

### P0-2 无 schema 版本号、无自动备份（数据安全） ✅ 已完成

**现象**：`db.py` 靠 `CREATE TABLE IF NOT EXISTS` + `SCHEMA_ADDITIONS` 补列完成"迁移"；没有 `schema_version` 表，无法表达"改列类型、删列、回填数据"。`erp.db` 是单文件，全项目 0 处备份逻辑（`grep backup` 仅命中状态回退变量）。

**影响**：① 下一次结构性变更（如金额改整数分）无法安全升级老库；② 误删、磁盘损坏、WAL 未 checkpoint 直接拷走 → 全量数据丢失。

**整改**：
```sql
CREATE TABLE IF NOT EXISTS schema_meta (version INTEGER NOT NULL, applied_at TEXT NOT NULL);
```
- 启动时读 `version`，按 `migrations/00X_*.sql` 顺序执行并在同一事务内写回版本号；
- 每次启动（或每日首次）自动备份：`sqlite3.Connection.backup()` → `data/backup/erp-YYYYMMDD-HHMM.db`，保留 30 份，超期自动清理；
- 界面「维护 → 备份/恢复」提供手动入口，恢复前强制再备份一次当前库。

### P0-3 排产附件用绝对路径，整体拷贝即失效 ✅ 已完成

**现象**：`v2/domains/schedule.py:271` 写入 `"file_path": str(target.resolve())`；`schema.sql` 注释亦写明"复制到 data/订单排产附件/ 后的**绝对路径**"。

**影响**：程序宣传"整体拷贝目录即可使用"，但换机器/换盘符/改目录后，所有图片、图纸、审批单全部打不开，且无提示。

**整改**：
- 落库改存**相对路径**（相对 `data/`），读取时 `data_dir / rel_path` 拼接；
- 增加一次性迁移：把已有绝对路径裁剪为相对路径（前缀匹配 `data/`）；
- 增加"附件体检"：扫描缺失文件，列表提示并允许重新指定目录。

### P0-4 无崩溃日志，故障只能靠截图 ✅ 已完成

**现象**：全项目 `grep "import logging|excepthook"` 零命中；`_run()` 只把异常弹窗，不落盘。

**影响**：用户（含你本人）遇到"点了没反应/闪退"时无任何可分析证据，与你在 Inventor 插件项目里"必须有日志+堆栈"的要求不一致。

**整改**：
- `logging` + `RotatingFileHandler` → `logs/app-YYYYMMDD.log`（保留 5 份，UTF-8）；
- 装 `sys.excepthook`、`threading.excepthook`、`qInstallMessageHandler`，未捕获异常写 ERROR 级堆栈；
- 错误弹窗增加「打开日志目录」按钮；日志里带版本号、DB 路径、操作名（`_run` 的 `label` 直接传入）。

### P1-5 显式声明的合计会被派生值覆盖

**现象**：`v2/domains/order.py:56-77` `_sync_totals()` 在 `amount_total/item_qty_total` 传 `None` 时按明细重算；`add_item / update_item / delete_item` 内部均以 `None` 调用（如 `order.py:255`）。导入时显式填写的价税合计，只要后续动一次明细就被改写。

**影响**：订单头与 ERP/合同金额不一致，且无痕迹。

**整改**：加两列标记 `amount_is_manual / qty_is_manual`（或 `head_source` 枚举），手工值只允许显式修改；派生只在"手工值为空"时写入，并在界面标注"自动/手工"来源。

### P1-6 金额与数量用 REAL 存储，存在浮点误差

**现象**：`orders.amount_total`、`order_items.amount/unit_price`、`qty_ordered` 均为 `REAL`；合计在 Python 侧 `round(..., 2)`。

**影响**：明细行数多时 `0.1+0.2` 类误差累积，导出 Excel 后与手算差 0.01，对账时会被质疑。

**整改**：金额改整数分存储（`amount_cents INTEGER`），显示层统一格式化；数量保留 3 位小数并用 `Decimal(str(x))` 参与运算；迁移脚本做一次全量换算并对账。

### P1-7 文档解析在主线程同步执行，大文件会假死

**现象**：`v2/ui/*.py` 与 `docread.py` 中 `QThread / ThreadPool / concurrent` **零命中**。PDF 抽表 + 图片 OCR（Tesseract）全在 UI 线程跑。

**影响**：30 页 PDF 或 4000×3000 手机照片，界面会"未响应"数十秒，Windows 可能弹"程序无响应"。

**整改**：`QThreadPool + QRunnable` 封装 `read_source()`，进度对话框（可取消），完成后回主线程弹预览；OCR 单独限流（一次一张）。

### P1-8 打包体积失控：476 MB，其中 200 MB+ 完全用不到

**实测构成（`_internal` 内 >5MB 文件）**：

| 文件 | 体积 | 业务是否需要 |
|---|---|---|
| `llvmlite/binding/llvmlite.dll` | **114.8 MB** | 否（numba 依赖，代码零引用） |
| `pymupdf/mupdfcpp64.dll` + `_mupdf.pyd` | **37.5 MB** | 否（仅 `v2/tests` 里 `import fitz`） |
| `pyarrow/arrow*.dll` | **30.4 MB** | 否 |
| `numpy.libs/libscipy_openblas64…dll` | 19.5 MB | 否（无 numpy 直接调用） |
| `PySide6/opengl32sw.dll` | 19.7 MB | 可裁（软件 OpenGL 兜底） |

**根因**：① `--collect-submodules v2` 把 `v2/tests` 一并收进包，测试文件里的 `import fitz` 把 PyMuPDF 整包拉入；② 未加 `--exclude-module`，pandas→numba→llvmlite 依赖链被动打包。实测运行期 `sys.modules` 中 `pandas/numba/llvmlite/pyarrow/pymupdf` **全部为 False**，即这些体积纯属浪费。

**整改**：
```python
"--exclude-module", "pandas", "--exclude-module", "numba",
"--exclude-module", "llvmlite", "--exclude-module", "pyarrow",
"--exclude-module", "matplotlib", "--exclude-module", "scipy",
"--exclude-module", "pymupdf", "--exclude-module", "v2.tests",
```
预计 476 MB → **110–130 MB**；同时对 `v2/tests` 加 `__init__` 隔离或用 `--collect-submodules v2.core,v2.domains,v2.ui` 白名单方式。

### P1-9 无用户体系，审计日志有表无值

**现象**：`audit_log.operator` 由调用方传，界面路径基本不传（`_run` 直接调服务方法，默认 `""`）。无登录、无当前操作人设置，也无审计查询界面。

**影响**：多人都能用同一台机，出问题无法定位"谁改的"；审计表形同虚设。

**整改**（轻量方案，不上权限系统）：启动时读 `config.json` 的 `operator`，未设置则弹一次"请输入使用人"；`_run` 自动注入 operator；「维护 → 审计日志」提供按实体/时间/操作人筛选的只读列表。

### P1-10 查询为内存过滤，数据量上去会卡

**现象**：`main_window_v2.py:770 _filtered()` 先取全量行，再在 Python 里做字符串包含匹配；无分页、无 `LIMIT`。

**影响**：当前 734 行无感；累计 2–3 年（数千单、数万行）后，每次切换视图都要全表读 + 全量过滤。

**整改**：过滤条件下推为 SQL `WHERE ... LIKE ?`（参数化），配套 `LIMIT/OFFSET` 分页；表格改用 `QAbstractTableModel` + `QSortFilterProxyModel`，只渲染可视行。

### P1-11 多机共享同一 SQLite 文件的隐患

**现象**：默认库在 exe 同目录 `data/erp.db`，开启 WAL。项目说明"整体拷贝即可使用"，实际很容易被放到共享盘给多人同时开。

**影响**：WAL 在网络盘上不可靠，并发写会 `database is locked`，极端情况损坏库文件。

**整改**：启动时检测多实例（命名互斥量 / lock 文件），第二实例提示"仅可只读打开"；文档明确"单机单用户"；若确需多人，走 P0-2 的备份 + 定时同步，或直接规划 C/S（WPF 方案下的天然优势，见第三章）。

## 三、改为 WPF 的缺陷与优点分析

### 3.1 对照表（以本项目实际技术需求为准）

| 维度 | 现状 PySide6 | WPF (.NET 8) | 判定 |
|---|---|---|---|
| 冷启动 | `--check` 1.41s；GUI 约 2–3s | framework-dependent 0.5–1s | **WPF 略优** |
| 部署体积 | 28.9 MB exe + 476 MB 目录 | self-contained 70–90 MB；依赖运行时 5–10 MB | **WPF 明显优**（尤其内网已统一 .NET） |
| 安装与升级 | onedir 手拷，无签名、无升级 | MSI/MSIX，可签名、可增量升级、可进企业软件中心 | **WPF 明显优** |
| Word 审批单 | `win32com` 调本机 Word，受 Office 位数/注册影响，失败回落 `startfile` | OpenXML SDK 生成更稳，Interop 类型安全；启动 Word 仍是 COM 但封装成熟 | **WPF 优** |
| Excel 导入导出 | openpyxl（成熟） | ClosedXML / NPOI（同样成熟） | 平 |
| PDF 抽表 | pdfplumber + pypdfium2，词框坐标可拿 | PdfPig 可拿字符坐标但表格重建需自写；iText 商用授权 | **Python 优** |
| 图片 OCR | Tesseract `image_to_data` 词框 + 自研聚类 | Windows.Media.Ocr（需语言包，词框能力弱）/ Tesseract.NET 绑定 | **Python 优** |
| 表格 UI | QTableView + 自绘/自写主题 555 行 | DataGrid 虚拟化默认、样式模板强、绑定省样板 | **WPF 优** |
| 高 DPI / 多屏 | Qt6 需配置 | manifest 一行 `PerMonitorV2` | **WPF 优** |
| 类型安全 | 无静态检查，靠 176 项测试兜底 | 编译期 + nullable + record，重构安全 | **WPF 优** |
| 迭代速度 | 改完即跑，无编译 | 编译 5–15s，XAML 热重载有限 | **Python 优** |
| 与 Inventor 插件协同 | 两套技术栈（Python + C#） | **完全统一**，可共享模型、校验、导出库 | **WPF 战略优势** |
| 跨平台 | 理论可跑 Linux/macOS | 仅 Windows | **Python 优** |
| 运行时依赖 | 自带解释器，零依赖 | 需 .NET 8 运行时；Win7 只能 .NET Framework 4.8 | Python 略优 |
| 报表/打印 | QPrinter + 手工排版 | FlowDocument / FixedDocument 原生分页打印 | **WPF 优** |
| 人才/维护 | Python 桌面相对小众 | .NET 桌面生态大、招人容易 | **WPF 优** |

### 3.2 迁移成本估算（按现有代码量）

| 模块 | Python 行数 | C# 估算 | 风险 | 说明 |
|---|---|---|---|---|
| `core`（db/schema/codegen/fields/excelio/errors） | ~3,300 | ~4,500 | 低 | EF Core 或 Dapper 直接映射；DDL 可沿用 |
| `domains`（bid/partcode/order/production/schedule/trace/maintenance） | ~2,600 | ~3,500 | 中 | 状态机、守恒、幂等约束必须逐条重测 |
| `ui`（主窗口/对话框/主题/查询面板） | ~4,151 | ~5,500 | **高** | XAML 重排 + MVVM，三栏工作台与右键菜单需重做 |
| `docread`（PDF/OCR/表格还原） | 744 | ~1,200 | **最高** | 核心算法资产，.NET 侧无等价实现 |
| 测试 | 2,894 | ~3,000 | 中 | 176 项需重写 |
| **合计** | **13,336** | **约 18,000** | — | 保守 6–10 周（单人全职） |

### 3.3 WPF 的主要缺陷（针对本项目）

1. **最值钱的算法要重写**：`docread.py` 744 行里，"PDF 词框坐标聚类还原列""OCR 标签噪声归一 + 模糊修复"是踩坑踩出来的，.NET 没有现成等价物。PdfPig 只给字符级坐标，表格聚类逻辑得从零再写一遍，且要用真实样本（306 单/734 行里的各种版式）重新调参。
2. **业务口径尚未冻结**：Q11/Q13/Q14 未拍板，此时重写等于把不确定口径固化两遍（Python 一遍、C# 一遍），返工成本翻倍。
3. **迭代速度下降**：改一个字段提示要编译 5–15s，XAML 绑定错误还是"静默失败"（输出窗口才有 binding error），排查比 Python 堆栈更难。
4. **第三方控件陷阱**：DataGrid 原生够用，但复杂表头合并、冻结列、打印预览往往要上 DevExpress/Telerik（商业授权数千元/年）。
5. **测试资产清零**：176 项测试不能直接复用，守恒/幂等这些"看不见但最要命"的约束会有一段裸奔期。
6. **生态断层**：将来若要做成本分析、统计回归、批量报价测算，pandas/numpy 的便利在 .NET 侧需要 MathNet/ML.NET 替代，能力不对等。
7. **部署前提变化**：内网若还有 Win7/Win8 机器，.NET 8 不支持，只能退回 .NET Framework 4.8（语言特性与库生态都受限）。

### 3.4 WPF 的主要优点（针对本项目）

1. **部署体验质变**：从"拷 500 MB 目录 + 可能被杀软误杀"变成"一个 MSI，点击安装，桌面快捷方式，可静默升级"。
2. **与 Office / Inventor 天然亲和**：审批单生成、Excel 导出、启动 Word、日后与 Inventor 插件共享"耐磨弯头/波纹管"模型库，全部同一套 .NET 生态，不用再维护 Python↔COM 的桥。
3. **强类型带来的长期可维护性**：13k 行动态代码靠测试保命；C# 有编译期检查 + `record` + `nullable`，重构 90 个方法的主窗口时不会"改一处崩三处"。
4. **UI 表达力与性能**：DataGrid 虚拟化、样式模板、绑定、打印分页都是开箱能力，不用像现在这样手写 555 行 QSS 主题。
5. **企业分发性更好**：代码签名、版本号、崩溃转储（WER）、性能计数器，IT 部门验收更容易过。

### 3.5 结论与建议路径

**结论：现在不建议全量重写；若确定要产品化/多人用，走"WPF 外壳 + Python 解析内核"的混合路线最划算。**

| 路径 | 内容 | 周期 | 适用前提 |
|---|---|---|---|
| **A（推荐先做）** | 保留 Python，完成 P0-1~P0-4 与 P1-8 打包瘦身 | 1–2 周 | 只要"能稳定用起来" |
| **B（中期推荐）** | Python 保留 `docread` 作为本地解析服务（HTTP/gRPC，localhost），WPF 重写 UI + domains | 4–6 周 | 确定要多机部署、要 MSI 安装、要与 Inventor 插件统一 |
| **C（谨慎）** | 全量 C# 重写（含 docread） | 6–10 周 | 必须彻底脱离 Python 运行时，且愿承担 PDF/OCR 重新调参风险 |

**判断是否该走 B 的三条硬指标**（满足 2 条以上再启动）：
1. 使用人数 ≥ 3 人，或需要放到共享服务器；
2. 需要正规安装包 / 企业软件中心分发 / 代码签名；
3. 半年内要与 Inventor 插件共用业务模型（耐磨件、波纹管参数、选材规则）。

否则，把 P0 四项做完、把 476 MB 压到 120 MB，投入产出比远高于重写。
