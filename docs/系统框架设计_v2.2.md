## 2. 两条链路（核心设计）

```
链路 A  询配码项目(虚值) ──提交用户──► 外部订单 DD-(可多张, batch_seq 1..n)
                                          │ 明细 qty_ordered = 实值
                                          ▼
                                      生产排产项目 ──► 溯源到「哪个询配码项目的哪一项」

链路 B  中标招投标项目 ──► 内部订单 ND-(一个中标项目仅一张)
                              │ 明细 qty_ordered = bid_items.qty（中标数量的实值）
                              ▼
                          生产排产项目 ──► 溯源到「哪个中标项目的哪一项」

            排产项目.source_bid_project_id = 来源标签（仅中标可挂，不携带数量）
```

**设计要点：不新开第二条数量链路。** 中标项目的数量必须先"翻译"成内部订单明细，再走与链路 A 完全相同的
`production_links → OrderService.available_qty() → Σallocated_qty ≤ qty_ordered` 校验。
这样超排拦截、拆批排产、解链回补、快照免疫对两类订单一视同仁，不会出现两套口径打架。

### 2.1 数量轨道 vs 溯源轨道（严格分离）

| 轨道 | 载体 | 说明 |
|---|---|---|
| 数量 | `order_items.qty_ordered` → `production_links.allocated_qty` | 唯一实值来源；内部订单取中标明细数量，外部订单取用户实际下单量 |
| 溯源 A | `order_items.source_code_item_id` → `code_items` → `code_projects` | 带着 `qty_reference` 虚值**仅作展示快照**，不参与校验 |
| 溯源 B | `order_items.source_bid_item_id` → `bid_items` → `bid_projects` | 带中标明细行号快照，回答"哪一项" |
| 标签 | `production_projects.source_bid_project_id` | 业务归属标签，不允许携带数量 |

## 4. 关键业务规则

### 4.1 内部订单（中标项目 → 排产数量）

| 规则 | 实现 |
|---|---|
| 只有 `status='中标'` 可生成 | `create_internal_from_bid()` 抛 `StateError`；`create_order(内部)` 同样校验 |
| 一个中标项目**一张** | 服务层 `internal_order_of()` 幂等检查 + 唯一部分索引；重复生成抛 `DuplicateError` |
| 明细数量 | `bid_items.qty`（中标明细数量，实值）；可用 `qty_overrides` / `line_ids` 覆盖或挑选 |
| 明细单价 | 沿用询报价口径 `对外报价 = purchase_price ÷ quote_ratio` |
| 溯源 | 每条明细 `source_bid_item_id` → 中标明细行；快照 `bid_line_snapshot` |
| 自动确认 | `auto_confirm=True`，内部订单无需用户确认即可排产（状态直接「已确认」） |
| 一键排产 | `create_project_from_won_bid()`：无内部订单则自动生成 → 建排产项目并挂中标标签 → 按剩余可排量把全部明细挂到 `production_links`；再点一次不会重复建单 |
| 拦截 | 未中标项目不能生成内部订单、不能挂排产；内部订单排满后超排同样被 `OverAllocationError` 拦 |

> 口径假设：项目中标视为**整单中标**，默认全部明细生成内部订单。若你们存在"逐行中标"，
> 用 `line_ids` 参数挑选即可，表结构无需改动（见 §12 Q2）。

### 4.2 一码多单

| 规则 | 实现 |
|---|---|
| 一个询配码项目可产生多张订单 | `orders.source_code_project_id` 无唯一约束；`create_from_code_project()` 可重复调用 |
| 批次编号 | `batch_seq = 该项目已有外部订单数 + 1`，界面显示「第 N 单」 |
| 状态允许继续下单 | 允许来源项目状态 `已提交 / 部分下单 / 已下单`；`refresh_status()` 按"是否被订单引用"回写 |
| 同一询配码项可重复下单 | 虚值 `qty_reference` 不扣减、不设上限；每张订单的实值各自独立守恒 |
| 订单可新增物资 | `source_code_item_id` 可空；「新建订单」明细行的来源项号留空即为订单新增物资 |
| 缺实值直接报错 | `create_from_code_project()` 缺 `qty_ordered` 抛 `ValidationError`，绝不复制虚值 |
| 统计 | `PartCodeService.statistics()` 返回 `order_count`、`batches`（每张订单实值合计/已排量）、虚值合计对照 |

### 4.3 状态机（`v2/core/models.py`）

```
招投标：草稿 → 已报价 → 中标 / 未中标 →（中标可作废）
询配码：草稿 → 已提交 ⇄ 部分下单 → 已下单 → 关闭（分批下单可多次回到部分/已下单状态）
订单：  草稿 → 已确认 → 已排产 → 生产中 → 已交付 → 关闭
生产：  待排 → 已排产 → 生产中 → 完工 → 已交付
```

### 6.5 单据维护：编辑 / 作废 / 删除（2026-11-06 · P0）

**解决的问题**：v2.2 交付时五个服务类只有 `create_* / add_* / set_status / unlink`，
录错一条明细或建错一个项目只能改库，无法作为正式系统日常使用。

| 项 | 实现 |
|---|---|
| 作用对象 | 右侧主结果表与明细下钻表都可点选；`TABLE_ENTITIES` 把 9 张表映射到 8 类实体，`_pick_target()` 取当前焦点表的行 ID，结果区「操作对象」标签实时回显；切换视图重置焦点到该视图主结果表 |
| 界面入口 | 新增「维护(&M)」菜单与左侧第 ⑥ 分组，4 个动作 `_edit_selected / _void_selected / _delete_selected / _show_audit`；全部经 `_run()` 包装（异常弹窗 + 全表刷新 + 状态栏回显） |
| 编辑 | `MaintenanceService.field_defs()` 生成带当前值的表单，复用 `ThemedDialog / FormDialog`（`ask(..., subtitle=...)`）；白名单之外的字段一律拒绝 |
| 作废 | 仅四类主单据（`voidable`），状态置 `models.VOID_STATUS`「作废」，填原因 + 二次确认；终态不可再编辑 |
| 删除 | 无跨实体引用且非运行态才允许；级联删除本级明细并逐行写 `delete_child` 审计；删外部订单后回写询配码项目下单状态 |
| 审计 | 「查看审计留痕」按当前对象或全系统查 `audit_log`，中文操作名 + before/after 摘要 + 可导出 |

**引用拦截矩阵**（`ENTITY_SPECS["refs"]`，有引用即抛 `ReferencedError` 并列出下游单号）：

| 实体 | 下游引用 |
|---|---|
| 招投标项目 | 内部订单、生产排产项目（来源标签） |
| 投标明细 | 内部订单明细 `source_bid_item_id` |
| 询配码项目 | 外部订单 `source_code_project_id` |
| 询配码明细 | 外部订单明细 `source_code_item_id` |
| 订单 | 排产关联（经订单明细，`where` 子查询） |
| 订单明细 | 排产关联 `order_item_id` |
| 生产排产项目 | 排产关联 / 工序任务（本级子表，级联前逐行留痕） |

**四条硬守卫**（`_guard_edit()` / `delete()`）：
1. 单号 `doc_no`、项码 `item_code`、行号 `line_no`、来源外键 `source_*`、
   `order_type`、`status` 不在白名单，改单即抛 `ValidationError`；
2. `order_items.qty_ordered` 不得改到小于 `Σ allocated_qty`；
   `production_links.allocated_qty` 不得超该明细剩余可排量 —— 保证 `integrity.check()` 恒通过；
3. 中标明细一旦进入内部订单，`qty / purchase_price / quote_ratio` 禁止回改
   （描述与备注仍可改，快照免疫）；
4. `code_items.qty_reference` 是虚值，可任意改，不触发任何守恒校验。

**作废口径**：作废是独立通道，不改 `models.TRANSITIONS` 正常流转；数据保留、状态终态。
查询窗口的状态下拉由 `SELECT DISTINCT status` 动态生成，「作废」自动可见。
明细行没有作废状态（`voidable=False`），改走删除。

**不改 schema**：`audit_log` 表与 `Database.log_action()` 早已存在，本版只新增服务层与界面动作，
老库无需补列、无需迁移；`models.VOID_STATUS` 是「作废」值的单一来源。
另在 `theme.dialog_shell()` 加了长标题截断（> 36 字省略 + tooltip）与副标题最小宽度，
防止编辑弹窗的长标题把副标题挤成竖排。

### 6.6 询配码明细 10 字段规范 + CSV/Excel 导入（2026-11-06）

**唯一定义处**：`v2/core/fields.py::CODE_ITEM_FIELDS`。字段顺序即业务表格顺序，
手动录入表单、导入模板表头、导出询配码文件、结果表列、编辑白名单全部由它派生，
杜绝「界面 10 列、导出 9 列、导入又按旧表头」的错位。

| # | 业务字段 | 数据库列 | 类型 | 处理 |
|---|---|---|---|---|
| 1 | 询价物料名称 | `inquiry_item_name` | TEXT | 新增；客户原始叫法，物料名称为空时自动兜底为主名称 |
| 2 | 商品编码 | `goods_code` | TEXT | 新增；建索引 `idx_ci_goods` |
| 3 | 物料编码 | `material_code` | TEXT | 新增；建索引 `idx_ci_material` |
| 4 | 物料名称 | `item_name` | TEXT | 复用；**唯一必填**，订单明细与溯源快照沿用此列 |
| 5 | 单位 | `unit` | TEXT | 复用；空值默认「件」 |
| 6 | 厂家价格(元) | `factory_price` | REAL | 新增；**仅询价信息，不是订单单价**，订单金额以 `order_items.unit_price` 为准 |
| 7 | 物料具体情况 | `item_detail` | TEXT | 新增；长文本 |
| 8 | 参考数量 | `qty_reference` | REAL | 复用；★ **虚值**，只统计，不参与下单/排产/守恒 |
| 9 | 备注 | `remark` | TEXT | 复用 |
| 10 | 技术要求 | `tech_requirement` | TEXT | 复用；长文本 |

历史字段 `spec / material / std_code / drawing_no` 不删（旧模板与老数据兼容），
仍可在「编辑选中记录」里维护，但不占 10 列主表单；系统锚点
`item_code / line_no / code_project_id / status` 一律不可由录入或导入覆盖。

**双通道录入**

| 通道 | 入口 | 行为 |
|---|---|---|
| 手动 | 左侧「添加询配码明细」/ 业务菜单 | `FormDialog` 两列网格 10 字段，仅物料名称必填，副标题明确虚值与价格口径 |
| 文件 | 左侧「导入询配码明细（CSV/Excel）」/ 数据菜单 | `ImportCodeItemsDialog`：默认带出主表当前点选项目 → 选文件 → 10 列预览（前 50 行）→ 逐行报告 → 确认后 `add_items_bulk()` 单事务写库 |
| 模板 | 左侧「下载询配码明细模板」/ 向导内「下载导入模板」 | 生成 `.xlsx` 或 `.csv`，表头严格 10 列并附示例行；「下载导入模板」菜单仍一次给出两张模板 |

**导入解析规则**（`core/excelio.py` + `core/fields.py`）：

1. 格式：`.xlsx / .xlsm`（openpyxl）/ `.csv / .tsv`；旧 `.xls` 明确提示另存。
2. 编码：UTF-8 BOM → UTF-8 → GB18030 → GBK → Big5，覆盖 Excel 另存的中文 CSV；
   分隔符用 `csv.Sniffer` 嗅探 `, \t ; |`，表头含制表符时优先 TSV。
3. 表头别名：归一化去空白/全角括号/尾部分隔符后匹配，例「厂家价格（元）」「厂家价」「出厂价」→ `factory_price`；
   「物资名称」「品名」→ `item_name`；「数量(虚值)」「预估数量」→ `qty_reference`；
   旧模板「规格/材质/执行标准/图号」仍映射到历史字段。未识别列忽略并在报告中列出。
4. 逐行报告：两个名称都空 → **跳过**（致命，给行号）；数值写成「面议 / abc」→ 按 0 落库并**提示**（非致命）；
   只填询价物料名称 → 自动兜底主名称并提示；完全无有效表头 → 直接拒绝。
5. 批量写库：`PartCodeService.add_items_bulk()` 先整批纯校验，再单事务逐行插入，
   中途失败全回滚；写一条 `import_code_items` 汇总审计（项目编号、行数、前 3 行名称、操作人）。
6. 表单兼容：`FormDialog(columns=2)` 两列网格；`ask()` 对 ≥8 字段自动两列，
   ≥12 字段自动加滚动区；`QWidget#FormScrollContent` 透明背景已进 QSS，滚动区与主窗口白卡片同色。

**口径守卫**：`factory_price` 与 `qty_reference` 都不参与任何守恒；
`test_15` 明确验证改虚值/价格/两个编码后 `production_links.qty_reference_snapshot` 保持 100、
订单实值合计仍 30、`integrity.check()` 通过。

**订单头 8 字段**（顺序即模板列顺序）：

| # | 业务字段 | 数据库列 | 类型 | 规则 |
|---|---|---|---|---|
| 1 | 订单项目编号 | `orders.project_no` | 文本 | 业务订单编号，**导入时作合并键**；系统单号 `doc_no`(DD-/ND-) 仍独立生成 |
| 2 | 需方单位 | `orders.customer` | 文本 | 复用旧 `customer` 列 |
| 3 | 订单类型 | `orders.order_type` | 枚举 | 外部订单 / 内部订单 |
| 4 | 订单状态 | `orders.status` | 枚举 | 草稿 / 已确认 / 待发货 / 已排产 / 生产中 / 发货中 / 已交付 / 已验收 / 关闭；作废走维护通道 |

| 6 | 交货日期 | `orders.required_date` | 日期 | 复用旧列，支持 `YYYY-MM-DD` / `YYYY/M/D` / Excel datetime |
| 7 | 物资数量 | `orders.item_qty_total` | 数值 | ★ **Q12 已确认：物资项目数**；留空自动 = 明细行数，不是 Σ 明细数量 |
| 8 | ERP订单编号 | `orders.erp_order_no` | 文本 | ERP 对接编号 |

**订单明细 9 字段**：

| # | 业务字段 | 数据库列 | 规则 |
|---|---|---|---|
| 1 | 物资代码 | `order_items.item_code` | 可由来源询配码项的物料编码 / 商品编码自动带出 |
| 2 | 物资名称 | `order_items.item_name` | 唯一必填；排产快照与主名称沿用此列 |
| 3 | 实际生产物资名称 | `order_items.production_name` | 留空 = 物资名称 |
| 4 | 规格 | `order_items.spec` | 复用旧列 |
| 5 | 单位 | `order_items.unit` | 留空 = 件 |
| 6 | 数量 | `order_items.qty_ordered` | ★**实值**，必须 > 0，排产唯一数量锚点 |
| 7 | 单价 | `order_items.unit_price` | 复用旧列 |
| 8 | 总价 | `order_items.amount` | 留空自动 = 数量 × 单价 |
| 9 | 参数描述 | `order_items.param_desc` | 可由来源询配码项的物料具体情况 / 技术要求带出 |

**17 列模板** = 上表 8 列 + 9 列，顺序为：
`订单项目编号 / 需方单位 / 订单类型 / 订单状态 / 价税合计 / 交货日期 / 物资数量 / ERP订单编号 / 物资代码 / 物资名称 / 实际生产物资名称 / 规格 / 单位 / 数量 / 单价 / 总价 / 参数描述`。

**分组规则**：每行 = 一张订单的一条明细。优先级
① 显式「订单分组」列（旧模板兼容）→ ②「订单项目编号」相同 → ③「ERP订单编号」相同 → ④ 都留空则每行独立成单。
分组键不是系统单号，DD-/ND- 仍由 `codegen` 生成。

**派生字段规则**：明细总价留空 = 数量×单价；头价税合计留空或组内不一致 = Σ 明细总价；
**头「物资数量」留空或组内不一致 = 明细行数（Q12 项数口径，2026-11-07 拍板）**；
若文件只有「价税合计」没有「总价」（真实销售订单表即如此），逐行把「价税合计」当作该行总价，头金额再汇总。
`OrderService._sync_totals()` 是唯一汇总入口；维护层改明细数量/单价/总价时自动重算
（改「数量」不会改变物资数量，因为它只数行数）。
显式填写且组内一致的值一律原样保留，不校验是否等于行数。
需要「Σ 明细数量」请用 `summary()['qty_ordered_real']` 或结果表「实值合计」列。

**三条硬口径不变**：
① 「数量」只写 `qty_ordered`，绝不读 `qty_reference` 虚值；
② 金额 / 合计字段**不参与** `Σ allocated_qty ≤ qty_ordered` 守恒；
③ 排产仍挂 `order_item_id`，`production_links` 快照免疫不受新增字段影响。

**真实数据兼容**：`销售订单汇总（24年7月-26年）.xlsx` 的「销售订单」表 22 列可直接导入 ——
`订单编号→订单项目编号`、`产品代码→物资代码`、`产品名称→物资名称`、`含税单价→单价`、
`价税合计→行总价`、`订单状态` 的 待发货/发货中/已验收 已并入 `OrderStatus.CREATABLE`。
实测 **306 张订单 / 734 行明细 / 0 致命行**，61 条提示均为同一订单编号下不同行的交货日期差异。

### 6.9 订单排产（2026-11-07 v2.4 · 取消「新建排产项目」）

**入口**：③ 订单管理 → 选中订单 → 下方明细表**右键某一项物资** → 订单排产对话框；
主结果表右键还有「选择物资建立订单排产」子菜单（✓ 已建 / ○ 未建）。
左侧操作列表与「业务」菜单的 ④ 生产排产组不再有「新建排产项目」，改为「★ 订单排产」并自动切到订单视图；
另有「查看订单排产单清单」只读表格。

**一物资一单**：`OrderScheduleService.ensure(order_item_id)` 幂等 —— 重复右键直接打开既有单据。
建单时自动创建一个 `production_projects` + 一条 `production_links`（分配量 = 该明细剩余可排量），
仍由 `ProductionService.link_order_item()` 做守恒校验；若该明细已被旧链路排满，则复用既有 link，不重复分配。

**对话框三项操作**：

| 操作 | 落地 |
|---|---|
| 新建生产排产审批 | `worddoc.build_approval_docx()` 用 python-docx 生成中文化审批单（订单头 8 字段 / 排产物资 9 字段 / 附件清单 / 编制-审核-批准栏），登记为「审批」附件；`open_in_word()` 优先 COM 显式启动本机 Word，Word 未装则回落 `os.startfile`（WPS 亦可）。绝不因 Word 缺失中断业务 |
| 图片导入 | Qt 自绘多选文件框（`theme.pick_paths`），复制到 `data/订单排产附件/<单号>/`，同名自动加序号 |
| 图纸导入 | 同上，过滤器覆盖 dwg/dxf/pdf/step/igs/ipt/sldprt 等 |

另可编辑「本次排产数量」（走 `update_allocation()` 守恒校验）与备注；所有操作即时写库，关窗不丢附件。

**★ 状态自动流转**：`OrderScheduleService._refresh()` 在每次建单 / 改量 / 撤销后重算 ——
当订单**所有明细都有对应订单排产单**且**实值全部排满**（`available_qty ≤ 0`）时，订单状态自动置为「已排产」；
撤销任一排产单或调低数量后按 `status_before` 原样回退，两次流转都写 `audit_log`。
`作废 / 关闭` 是终态不自动覆盖；建单前本就是「已排产」（旧链路）的订单不会因只补一张单而倒退状态。
`ProductionService.link_order_item()` 旧行为保留给「中标一键排产 / 关联订单明细」两条既有链路，
新链路在建单事务内先静默还原那次中间态，再由 `_refresh()` 统一判定，避免审计噪音。

**硬口径**：`order_schedules.allocated_qty` 只是展示快照；`qty_ordered` 仍是唯一实值锚点；
询配码虚值依旧不进排产；`production_links` 快照字段不受影响。

### 6.10 添加订单 · 图片 / 表格 / PDF / Word（2026-11-07 v2.5 追加）

订单管理页面「刷新」左侧新增「添加订单」按钮（仅订单视图显示；左列 ③订单管理 与业务菜单同步）。
对话框选文件 → `core/docread.read_source()` 识别 → **17 列标准标签可编辑预览** → 逐格修正 → 建单。

| 来源 | 识别策略 |
|---|---|
| 表格 xlsx/xlsm/xls/csv/tsv/txt | 逐工作表找「表头命中订单字段最多」的一张（可跳过标题/空行）；旧 .xls 先经本机 Excel 转 .xlsx |
| Word docx/doc | 优先取表头能命中的表格；无表格则按正文「键：值」解析（同一「物资名称」重复出现即下一行明细）；旧 .doc 先经本机 Word 转 .docx |
| PDF 文字型 | pdfplumber 抽表（有线框时）；否则按**词框坐标聚类还原行列**（中文 PDF 抽出的文本常是单空格，纯文本切分拿不到列）；再不行退回「键：值」 |
| PDF 扫描件 / 图片 png/jpg/bmp/webp | Tesseract（chi_sim+eng）`image_to_data` 词框 → 同一套行列聚类；表头经噪声归一（`”数量`→数量、中文间空格去除）+ 模糊修复（`数=`/`效量`→数量，要求最佳相似度明显优于次优） |

关键设计：

* **统一口径**：识别结果经 `to_canonical()` 摊成 17 列标准标签（缺列补空），确认后仍交
  `OrderService.import_orders()` —— 与「导入订单」共用别名解析、分组、派生金额、逐行报告，
  绝不另造第二套字段口径；「价税合计」列自动承担真实销售订单表的行级金额回填。
* **可编辑兜底**：OCR/解析不完美（如「件」认成「+」）时在预览表内直接改，改完即时重算报告。
* **一张单据 = 一张订单**：所有行都没有项目编号/ERP 编号时，自动注入「订单分组 = 文件名」，
  避免解析层「都留空 → 每行独立成单」把一张单拆成 N 张；一旦文件里有编号则完全按编号分组。
* **降级策略**：Tesseract 未安装时给明确指引（装 Tesseract 或设 `TESSERACT_CMD`），
  表格/Word/文字型 PDF 不受影响；旧 .doc/.xls 转换失败也会说明原因，不静默失败。
* OCR 为**尽力识别**：文字模糊、斜拍、艺术字可能识别不准，预览可改，最终以人工确认为准。

### 6.14 订单来源（2026-11-07 v2.9 · 张哥给定）

**是什么**：`orders.order_source`，记录这张订单是**通过哪个渠道来的**，比如招投标中的标、
北电电力下单、厦门龙净下单、京东平台下单。它是**订单头属性**，不是溯源外键。

**与既有「来源」的区别（不要混）**：

| 字段 | 含义 | 谁写入 | 能否为空 |
|---|---|---|---|
| `source_code_project_id` | 这张外部订单由哪个**询配码项目**下单产生 | 系统按链路写 | 可空（手工订单） |
| `source_bid_project_id` | 这张内部订单由哪个**中标项目**生成 | 系统按链路写 | 内部订单必填 |
| `order_source` | 这张订单的**销售渠道**（招投标 / 北电电力 / …） | 用户选择或手输 | 可空 = 未标注 |

前两个是溯源锚点，维护界面**禁止编辑**；`order_source` 是业务属性，**可以改**。

**取值口径**：唯一来源 `v2/core/order_fields.py::ORDER_SOURCES = ("招投标","北电电力","厦门龙净","京东平台")`。
控件是**可编辑下拉**（`QComboBox` + `setEditable(True)` + `NoInsert`）：
下拉四选一，或直接输入新渠道，**按原文落库**。数据库**不加 CHECK 约束** ——
每加一个渠道不必重建表，也不需要发版；代价是脏值靠输入纪律（下拉已覆盖常用项）。

**三个入口**：

| 入口 | 行为 |
|---|---|
| ① 新建订单（`NewOrderDialog`） | 订单头新增「订单来源」可编辑下拉，位置在「需方单位」之后；留空 = 未标注 |
| ② 添加订单（`AddOrderDialog`） | 顶部「订单来源」= **本批默认来源**，只补文件里没填的行，**不覆盖**文件自带值；改完自动重算预览 |
| ③ 导入订单（`ImportOrdersDialog`） | 文件里带「订单来源」列（别名：来源渠道 / 订单渠道 / 销售渠道 / 渠道 / 来源平台）即自动识别；模板仍是 17 列不变 |

**自动规则**：

- 内部订单（中标项目生成）来源**缺省回填「招投标」**——它只可能来自中标，不需要用户再选；
- 外部订单**不猜**：历史 306 单来源留空 = 未标注，要标注请在订单上编辑或重导；
- 订单主结果表新增「订单来源」列（在「需方单位」后），关键字搜索已包含该列；

内部订单空来源回填「招投标」；幂等，可重复执行。真实库已在 2026-11-07 19:33 备份后升级（306 单不变）。

### 6.21 自动更新：清单 + 全量 zip + 目录交换（2026-11-08 v3.1.0 · 方案 B）

**形态约束与选型**：程序是 PyInstaller onedir 绿色目录（178 MB），`data/`（数据库/
附件/日志）在程序目录内，Windows 不允许覆盖运行中的 exe —— 因此不走安装器路线，
选**半自动更新**：保持绿色版形态，用户感知为「提示 → 点一下 → 自动重启进新版」。

**发布侧**（`tools/release.py --note "…"`）：打包 → 压 zip（顶层为程序文件夹，
排除 `data/ logs/ _update_staging/ _update_downloads/ _old_*`）→ SHA256 →
`manifest.json`（`version / zip / sha256 / note / date`，zip 相对 manifest 目录解析）
→ 产物在 `dist/release/`，把两个文件放进更新源即完成发版。更新源 = 任意用户程序
读得到的位置：本机目录 / `\\服务器\共享\` / HTTP 静态目录 / 网盘同步盘。

**用户侧**（`v2/core/updater.py` + `v2/ui/update_dialog.py`）：
- **更新源配置**：`data/updater.json`（帮助 → 设置更新源…），清空 = 关闭自动检查；
- **检查**：启动 3 秒后台自动一次（无源/出错/无更新一律静默），帮助菜单可手动触发；
  `fetch_manifest` 支持 file/UNC/HTTP，`check()` 永不抛异常（三态 update/latest/error）；
- **版本比较**：`parse_version` 数值化（`3.0.1` < `3.1`，`v2.9.4-beta` → (2,9,4)）；
- **更新流程**：`download_zip`（HTTP 分块 / 本地复制，**SHA256 不过即删残留并报错**）
  → `unpack_zip` 到 `<base>/_update_staging/` → 写 `_update_marker.json` →
  **启动 staging 里的新版 exe：`--apply-update`（冻结 exe 自身即更新器）** → 主程序退出；
- **目录交换**（更新器进程，`apply_update_from_marker`）：
  ① 等 `data/` 可整体移动（= 旧进程退出、SQLite WAL 锁释放，上限 60s）；
  ② `target/data` → `<base>/_update_data_keep`（同卷移动，瞬时）；
  ③ `target` → `_old_<时间戳>`（备份）；④ staging → target；⑤ data 归位；
  ⑥ 启动新版 exe；⑦ 清理历史 `_old_*` 与下载残留。
  **任何一步失败 → 自动回滚**（旧目录原位、data 归位），旧程序照常可用，
  全程写 `_update_apply.log`。
- 关键坑：更新器必须从 **staging 目录**运行（旧目录里的 exe 镜像被锁，不能在
  重命名目标目录时还住在里面）；`--apply-update` 分支在单实例锁获取之前处理。

**回归**：`v2/tests/test_updater.py` **16 项** —— 版本比较、清单三态、相对 zip 解析、
缺字段/坏 JSON 拒绝、下载进度与 SHA256 失败清理、解压定位程序目录、
**目录交换成功路径（data 原位保留 + `_old_` 备份 + staging 腾空）**、
**失败回滚（旧目录与 data 完整还原）**、marker 文件入口、备份清理、配置读写、
对话框冒烟。v2 全量 **319 passed + 24 subtests**。

### 6.22 云同步盘占位文件读取修复（2026-11-08 v3.1.1 · 用户第 10 轮反馈）

**现象**：从资源管理器选择 OneDrive 文件后程序读不出来（点了没反应 / 界面卡住）。

**根因（本机实测，非推测）**：

| 证据 | 数据 |
|---|---|
| 云占位文件占比 | `D:\OneDrive` 根目录 189 个文件里 **166 个**带 `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`（0x400000），部分另带 `OFFLINE`（0x1000）/ `RECALL_ON_OPEN`（0x40000） |
| 文件属性 | `is_file()` / `stat()` 全部正常、能看到真实大小，但本地只有壳 |
| 首次读取 | `open().read(8)` 耗时 **1.6s**（触发水合），`read_bytes()` 曾抛 `OSError [Errno 22] Invalid argument`；离线样本 **45 秒仍未完成**（复现脚本被超时杀掉 2 次） |
| 文件框 | `make_file_dialog()` 设了 `DontUseNativeDialog=True`，Qt 自绘不走 Windows Shell，拿不到 OneDrive 的「仅联机」集成；侧边栏只有 home/current/data，无云盘入口 |

**三层修复**：

1. **文件框层** `v2/ui/theme.py`：`use_native_file_dialog()` —— Windows 默认用**资源管理器原生对话框**（Shell 自带 OneDrive 集成，选中即触发水合），侧边栏 `_sidebar_urls()` 自动补 `OneDrive / OneDriveCommercial / OneDriveConsumer / %USERPROFILE%\OneDrive`；`QT_QPA_PLATFORM=offscreen|minimal` 自动回退自绘（保证离屏自检），`PQS_FILE_DIALOG=qt` 可强制自绘。
2. **适配层** `v2/core/cloudfile.py`：`is_placeholder()` 只读 `lstat` 属性位（零成本、不触发水合）；`ensure_readable()` 在**守护线程**里 `copyfile` 到 `pqs_cloud_cache/<hash>/<原名>`（复制即触发水合并落实体），按 路径+大小+mtime 命中复用；主线程每 50ms `th.join(0.05)` 并回调 `tick`（UI 传 `QApplication.processEvents`）保持界面可响应，最长 30 秒；超时 / 大小不符抛 `ValidationError`，提示「资源管理器右键 → 始终保留在此设备上」。副本**文件名与扩展名不变**，openpyxl / python-docx / pdfplumber / PIL 无需改动。
3. **入口层**：`theme.pick_path/pick_paths` 选中后做水合预热（**返回原始路径**，路径字段存的仍是用户选的真实位置）；`docread.read_source()`、`excelio.import_rows()`、`schedule.add_files()` 两处附件复制、`updater.fetch_manifest()` 与本地更新包 `download_zip()` 全部先调 `ensure_readable()`。保存目标（`mode=save`）/目录选择不做水合。

**边界处理**：源文件本来就是 0 字节（空白工作簿）按「源/副本大小一致」判成功，不误判；`REPARSE_POINT` 单独不算云占位（本地符号链接也带该位）；非 Windows 平台恒按本地文件处理；缓存副本在系统临时目录，不污染业务 `data/`。

**回归**：`v2/tests/test_cloudfile.py` **32 项**（属性位 8 / 水合缓存超时 10 / 云盘根目录 2 / 文件框 8 / 各读取入口 4）；模拟云占位 + 真实 xlsx 端到端 `read_source` 解析 2 行命中 5 字段、`excelio.import_rows` 2 行，全通过。v2 全量 **351 passed + 24 subtests**。

### 6.30 自动更新链路修复（2026-11-10 v3.4.4 · 用户第 19 轮）

**故障现象**：部署版 v3.4.2 点「立即更新」到 v3.4.3 时弹
`ValidationError: 更新包里找不到主程序：ProductSuite_v2.2.exe`，程序未做任何改动。
同时 `D:/Programs/_update_apply.log` 显示 11-08 / 11-09 / 11-10 共 4 次更新器都因
`[WinError 5] 拒绝访问 …\_internal\PySide6\MSVCP140_1.dll` 失败并回滚 —— 是两条
独立但同样阻断升级的缺陷，v3.4.3 只解决了「改名」这一层，未触及它们。

**根因 A（本次直接报错）**：`unpack_zip()` 旧实现只在
`len(dirs) == 1 and len(entries) == 1` 时返回该子目录，否则返回暂存根。
`D:/Programs/_update_staging/` 里同时留着 19:57 的 `ProductSuite_v2.2/`
（上次回滚残留）与 21:08 的 `订单管理工作台/`（本次解压），于是返回暂存根；
旧版 3.4.2 在暂存根下找 `ProductSuite_v2.2.exe` 自然失败。

**根因 B（历史 4 次失败）**：更新器进程由 `staging/xxx.exe --apply-update` 启动，
它加载的 `_internal/*.dll` 就位于 staging 内；第⑥步 `shutil.move(staging → target)`
要求重命名一个含被进程占用文件的目录，Windows 直接拒绝。

**修复（`v2/core/updater.py`）**：

| 位置 | 改动 |
|---|---|
| `prepare_update()` | 解压前 `shutil.rmtree(staging_root)` 清空历史残留；进度提示细化为「清理暂存区 → 解压」 |
| `unpack_zip()` | 不再依赖目录数量：遍历子目录，按 `st_mtime` 倒序挑**第一个含主 exe** 的目录（`find_main_exe` 判定）；扁平 zip 仍回退暂存根 |
| `apply_update_from_marker()` ③ | `shutil.move(staging, target)` → `shutil.copytree(staging, target)`：读自身占用的文件是允许的，target 此时已被备份移走、可直接新建 |
| 同上（失败分支） | 先 `rmtree` 掉可能只复制了一半的 target，再 `_move(backup, target)`，避免旧目录被嵌套进 target |
| 成功后 | `cleanup_old_downloads(base, keep=2)` 回收历史 zip；staging 因进程占用不自删，日志明确「保留至下次更新前清理」 |

**为什么旧版 3.4.2 也能吃到修复**：旧版只负责 `prepare_update`（下载/解压/写
marker/启动 staging 里的新 exe），真正执行目录交换的是 **staging 里的新版冻结 exe**，
其 `--apply-update` 分支在 `app_v2.main()` 最前面、不占单实例锁。所以根因 B 的
修复立刻生效；根因 A 则由「发布侧清空本机暂存区」+「新版 prepare 清空暂存区」
双保险解决（旧版本身的 `unpack_zip` 无法回改）。

**刻意不改**：schema 仍 v6、`data/` 原位、部署目录名、兼容别名 exe、单实例互斥体名、
zip 顶层目录 `订单管理工作台/`（用户要求的程序集名称）。

**验证**：新增 `v2/tests/test_updater_swap_v344.py` **13 项**（脏暂存智能挑选 /
prepare 清空 / 扁平 zip / copytree 源码与行为 / 半成品回滚 / 下载缓存回收 /
主 exe 发现优先级）；同步 `test_updater.py::test_10` 的「staging 已腾空」断言为
「staging 保留」；pytest v2 **504 passed + 160 subtests**、v1.5 **36/36**。
发布前另做**真实冻结 exe 进程级 E2E**（模拟脏暂存 + 真进程占用 DLL），详见 §10。

### 6.32 采购合同金额取自合同文档（2026-11-11 v3.4.6 · 用户第 21 轮）

**问题（真实库复盘）**：v3.4.5 的 `import_contract_files()` 建档时直接写
`"amount": order.get("amount_total") or 0`。部署库里合同
`20261107KYCN-B-027` 台账金额 `18778.00` 正好等于关联订单 308 的总额，
而合同原文写的是：

```
总计：
人民币：壹万肆仟肆佰捌拾肆圆整
（含税不含运，其中不含税金额12817.7元，增值税金额1666.3元）
14484
```

正确合同金额应为 **¥14,484.00**。同目录 `20261110KYCN-B-028` 系列为 **¥5,692.00**，
对应订单 309 总额却是 ¥49,423.00。合同金额与订单金额本无必然相等关系。

**解析层 `v2/core/contract_amount.py`（新增，纯只读）**

| 通道 | 做法 |
|---|---|
| Word `.docx/.docm` | python-docx 段落 + 表格逐行 |
| 旧版 `.doc/.wps/.xls`（OLE 二进制） | **不依赖 Office**：整文件 UTF-16LE / GB18030 解码后抽「含中文的连续片段」+ 裸数字行；Word COM 仅作识别不到时的增强通道 |
| Excel `.xlsx/.xlsm/.et` | openpyxl `data_only=True` 逐工作表逐行 |
| CSV / TSV / TXT | 多编码探测后逐行 |
| PDF | pdfplumber 文字层 + 抽表（PyPDF2 兜底）；无文字层时 pypdfium2 + Tesseract OCR 前 2 页（可用时） |
| 图片 | Tesseract OCR（可用时，尽力而为） |

统一降成「行文本」后，三类线索按置信度取最优：
① 明确标签 + 数字（`合同金额 / 合同总金额 / 价税合计 / 合计金额 …`，score 100）；
② **中文大写金额**（`壹万肆仟肆佰捌拾肆圆整 → 14484`，score 95，支持角分）；
③ 弱标签（`总计 / 合计 / 小写 / 人民币`）与标签行后 3 行内的裸金额（score 80 / 55）。
标签后数值优先于标签前数值，避免「合同编号 2026…」抢先命中；日期数字先抹除。

**干扰项硬排除**：`不含税金额12817.7元`、`增值税金额1666.3元`、`单价 | 3552`、
`合同额20%`、`已付/预付/余款` 等负面词连同其后 20 字符内第一个数字整段抹除，
再找金额候选。明细表表头 `总价（元）` 不列为强标签，避免逐行明细被误判成总额。
解析失败一律返回 `amount=None`，**永不抛异常、绝不猜数**。

**服务层 `domains/contract.py` 口径**

- `import_contract_files()` 建档不再传 `amount_total`，先建 0，再由
  `_apply_doc_amount()` 按「分组内置信度最高的文档命中」写入；
  返回新增 `amounts`（每份合同的金额摘要）与 `amount_missing`（未识别清单）。
- `_linked_order_total()` / `_amount_is_auto()` 里的订单总额**只用于识别历史错误值**：
  台账金额等于订单总额或为 0 视为自动来源 → 用文档金额覆盖；识别不到则清 0 并提示补录。
  用户手工填过（与订单总额不同且非 0）的金额一律保留，并在结果栏说明差异。
- 新增 `refresh_amount_from_files()`：按该合同已归档的全部文件重算金额，
  供历史台账一键纠正；合同管理窗口新增「重读金额」按钮。
- 金额写入写审计 `set_amount_from_doc`（before/after + 标签 + 源文件），
  `import_signed` 日志补 `amount` / `amount_source`。

**UI**：采购合同管理窗口「导入合同」结果栏与生产排产「导入采购合同」返回文案
都追加金额及来源摘要（`amount_summary()`）；未识别到总金额时明确提示人工补录。

零迁移：`schema_meta` 仍 v6、18 张表不变、`data/` 原位保留、更新链路与品牌不变。

### 6.33 订单盈亏与多供应商采购归集（2026-11-18 v3.5.0 · 用户第 22 轮）

**问题**：一张订单含多项物资、不同物资与不同供应商签不同采购合同时，旧模型的
`purchase_contracts.order_id` 只是订单级单值外键，无法把采购成本归集到物资行；
`context()` 生成 Word 合同时读整单明细且用**销售单价**；`_contract_for_order()`
「复用该订单第一份合同」会把第二家供应商误归到最早那份台账。全系统只有
`BidService.summary()` 在招投标项目级算报价毛利，订单级利润率与图表均不存在。

**张哥拍板的三条口径（写进 `v2/domains/profit.py`，UI / 图表 / 导出一律复用）**

| # | 口径 | 实现 |
|---|---|---|
| 1 | 销售额取**明细为准** | `sales = Σ order_items.amount`（为 0 回退 `qty × unit_price`）；与订单头 `amount_total` 差 >0.01 时给 warning，不静默挑一个 |
| 2 | 金额统一**含税** | 采购额 = Σ 已签合同分配明细的含税金额；`tax_included=0` 的合同参与统计时 `profit_rate=None` 且告警「不出数」 |
| 3 | 未覆盖标**不完整** | `coverage = 已分配明细数 / 明细总数`；`complete=False` 时利润率标注「不完整」，未采购物资绝不当 0 成本 |

**数据层（唯一一次 schema 升版：v6 → v7）**

```sql
CREATE TABLE purchase_contract_items (
  contract_id   INTEGER NOT NULL REFERENCES purchase_contracts(id) ON DELETE CASCADE,
  order_item_id INTEGER NOT NULL REFERENCES order_items(id)         ON DELETE CASCADE,
  qty           REAL NOT NULL CHECK (qty > 0),
  unit_price    REAL NOT NULL DEFAULT 0,   -- 含税采购单价
  tax_rate      REAL NOT NULL DEFAULT 0,   -- 仅记录，不参与利润率
  amount        REAL NOT NULL DEFAULT 0,   -- q2(qty × unit_price)
  UNIQUE (contract_id, order_item_id)
);
```

★ **不在 `order_items` 上加采购单价列**：一条物资可分两家供应商、分两批采购，
单值字段表达不了；采购成本是按 `order_item_id` 汇总出来的**派生值**，
存成明细属性会造出第二个金额源，与「数量守恒唯一来源是 `qty_ordered`」冲突。
`purchase_contracts.order_id` 保留作兼容 / 主关联展示，但**不再是归集依据**。

迁移 `migrations.py::v7_contract_items_backfill()`：只对「唯一明细 + 已签订 +

### 6.34 合同明细表自动解析与物资分配建议（2026-11-18 v3.5.1 · 用户第 24 轮）

**问题**：v3.5.0 的采购合计按 `purchase_contract_items` 分配明细归集，但多明细历史合同
（如 `20261107KYCN-B-027` 挂 2 项物资）按「不猜不摊」口径没有回填，用户须逐行手工
勾选物资并敲数量、含税单价。用户问「能否自动进行物资分配并填充单价」。

**根因（有日志证据）**：`core/contract_amount.py::_iter_lines()` 对 `.doc` 的策略是
「先 `_lines_from_ole_binary()`，有行就 `return`」（L387-392），因此**永远不会走
`_lines_from_word_com()`**；而 OLE 二进制扫描只提取出 UTF-16LE 中文片段，实测
`20261107KYCN-B-027.doc` 仅得 35 行（抬头 / 编号 / 大写总额 / 地址 / 乱码），
**Word 表格中的物资明细一行都没有**。即便走 COM，旧实现也只把
`table.Range.Text` 追加进一个字符串再 `splitlines()`，**行列结构被拍平**，
无法区分「哪几个单元格属于同一物资行」。所以自动分配必须新开一条结构化读取通道。

**实现（`core/contract_items.py`，schema 仍 v7、零 DDL 改动）**

| 层 | 做法 |
|---|---|
| 表格读取 | `.doc/.wps/.rtf/.xls` → Word/WPS COM 遍历 `doc.Tables`、`Cell(r,c).Range.Text` 逐格取；合并单元格取不到时留空。`.docx` → python-docx `t.rows/cells`；`.xlsx` → openpyxl `values_only`；`.csv/.tsv` → csv 模块。后三条**不依赖 Office** |
| 表识别 | 表头别名映射（物资名称 / 规格 / 数量 / 单价 / 总价 / 单位 / 商品编码），要求同时有 `name + qty + (unit_price or amount)` 才认作采购明细表；含「总计 / 合计 / 人民币」的行跳过。真实合同 6 张表里准确命中第 2 张，技术规格表（无单价）不误选 |
| 数值派生 | 只有总价时 `unit_price = q2(amount / qty)`；只有单价时 `amount = q2(qty × price)`；千分位 / 「元」/ 单元格结束符 `\r\x07` 全清洗 |
| 匹配打分 | 名称完全一致 +60 / 包含 +35；**类型词**（弯头 / 三通 / 补偿器…，长词优先）相同 +40、冲突 −60；规格数字（DN254 / 内径254）交集 +15；数量一致 +12；单位 +4；剩余可采购量够 +6、超 −20；唯一候选 +10。<40 分**不自动勾选** |
| 约束 | 无单价绝不填 0；`qty ≤ remaining_qty` 否则截断并告警；同一合同对同一订单明细只能一行（`UNIQUE`），多行命中时合并 qty/amount 并反算加权单价；Σ 明细与台账金额对账，偏差只告警不阻断 |
| 写库边界 | `suggest_items_from_file()` **只产出 `suggestions / specs / unmatched / warnings`，零写入**；写库仍由 `set_contract_items()` 在用户点「保存分配」时完成 |

**为什么名称对不上仍能配**：合同写「双金属复合弯头 / 双金属复合三通」，订单写
「七段合金衬弯头\\LKT09-… / 五段弧三通\\LKT08-…」，全称零交集；靠类型词 +
数量 2 一致 + 单位「件」+ 数量守恒，两行分别得 62 分（高置信），类型冲突项被
−60 排除。`20261110KYCN-B-028` 唯一明细 + `DN254` 规格数字吻合，得 87 分。

**实测（真实 .doc，只读、mtime 未变）**：
`20261107KYCN-B-027` → 2 行（¥7,104 + ¥7,380 = ¥14,484）、
`20261110KYCN-B-028` → 1 行（¥5,692）；两份均 100% 匹配、未匹配 0 行、
与台账金额差额 ¥0.00。服务层接到建议后 `purchase_contract_items` 仍为 0 行，
只有调用 `set_contract_items()` 才落库，落库后 `order_summary()["purchase_total"]`
= ¥14,484 / ¥5,692，`complete=True`。

**UI**：`ui/contract_items_dialog.py` 动作栏新增「从合同文档自动匹配」，
预填勾选 / 本次数量 / 含税单价 / 含税金额 / 备注（标「需复核」），
hint 显示来源文件、表序、明细行数、金额对账、未匹配行数；未匹配行**保持用户
原输入不擅自清空**；一份合同跨多单时切到对应订单再点一次即可。

**回归**：`test_contract_items_v351.py` 22 项（解析三通道 / 单价派生 / 无表格诊断 /
名称不一致匹配 / 类型冲突 / 无单价不勾 / 数量截断 / 合并加权 / 对账告警 /
服务层不写库 / 跨订单排除 / 离屏 UI 预填→保存 / 真实 .doc COM 集成）。

```

github:wodeya163/rongsheng-order-workbench@v3.5.4    锁定 tag（回滚 / 灰度）
https://…/manifest.json                              HTTP 静态目录
```

`updater.fetch_manifest()` 对 `github:` 源先读 `latest/download/manifest.json`；清单里的 `zip` 由发布脚本改写成**该 Release 的资产绝对 URL**（带 tag，不随 latest 漂移），因此客户端无需调 GitHub API，也没有中文资产名 percent 编码的歧义。若清单里写的是相对名，客户端按 `github_asset_url()` 自动补全；绝对 URL 会做 `github.com` / `githubusercontent.com` 域名白名单校验。
